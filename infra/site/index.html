Read this before you press it. No two runs of this page are the same, and that is the point. Five agents work at once against one live cluster, so which agent wins a race, which duplicate is caught first and which defect survives into the returned application are decided while you watch. Some hazards will not fire on your run. A lane that failed identically every time would be a recording, not a system.

CORTEX coordination layer

What CORTEX does during one task.

These five actions are the mechanism. The animation below uses the same actions reported by the running agents.

  1. Describe workThe agent submits the intended change before editing files.
  2. Check meaningA vector search finds semantically equivalent work, even when ticket wording differs.
  3. Claim filesThe duplicate check and every required file claim commit in one serializable transaction.
  4. Re-planA blocked agent receives the holder and intent, then chooses different work instead of polling.
  5. Store outcomeCompleted or abandoned work becomes repository-scoped memory for later agents.

Why this workload can fail.

The tickets create three different coordination hazards. Worktrees handle none of them before agents start editing.

Two duplicate pairsP2 and P6 request the same outcomes using different wording and different modules.
Three agents, one fileC1, C2 and C3 change separate behaviors inside orders/repository.js during overlapping windows.
Two decision chainsShipping and refund work must reuse choices made earlier by the money and payment tasks.
